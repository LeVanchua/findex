# Лабораторна №5: що я побачив у досліді з GIL

Я продовжив `findex` із лабораторних 1–4. Кожен робітник отримує список **шляхів** до частини документів, читає їх сам, токенізує і створює свій словник термінів. Наперед призначений `start_id` не дає двом робітникам записати однаковий ID. Після завершення я об'єдную результати у батьківському процесі, сортую постінги та перевіряю дублікати. При цьому серійна і паралельні збірки створюють однаковий індекс.

## Чому потоки з GIL не прискорили індексацію

Звичайний CPython 3.12 має Global Interpreter Lock. Для Python-коду обробки токенів і словників у конкретний момент виконувати байткод може лише один потік. У моєму замірі з 1 потоком було 0.229 с, а з 8 — 0.399 с. Додаткові потоки змагаються за GIL, перемикаються й додають накладні витрати. Це насамперед CPU-bound робота, а не очікування мережі або диска; під час I/O GIL часто звільняється, тому там результати могли б бути іншими.

## Чому процеси можуть виграти і яка їхня ціна

Кожен процес має власний інтерпретатор Python і GIL, тому окремі ядра можуть справді токенізувати паралельно. При 8 процесах медіана wall time впала до 0.211 с проти 0.245 с послідовно (1.16×). Проте сумарний CPU time виріс із 0.245 до 1.259 с: я витратив **більше обчислювальних ресурсів**, щоб закінчити трохи раніше. Дочірні процеси мають окрему пам'ять. Заміри RSS у таблиці — лише батьківського процесу; вони не означають, що *загальна* пам'ять системи з процесами менша. Часткові індекси серіалізуються через pickle і передаються назад, що також коштує часу й пам'яті. Через `spawn` старт процесів дорожчий, ніж старт потоків. Саме тому процеси з одним воркером (0.396 с) програють простій послідовній збірці.

## Закон Амдала та merge

Навіть нескінченна кількість ядер не прискорює ту частину програми, яка виконується тільки послідовно. У моєму алгоритмі до послідовної частини належать перерахування файлів, підготовка шматків та фінальний `merge`. Сам `merge` займав приблизно 0.002–0.003 с, але це не весь serial overhead: сюди не включені створення процесів і передача даних. Тому реальне прискорення далеко від ідеальної прямої на графіку. На 9 процесах стало 0.212 с, практично так само, як 0.211 с на 8: масштабування досягло межі, а витрати запуску й передачі даних продовжили зростати.

## Що змінилося у Python 3.13t

Я встановив `uv python install 3.13t` і перевірив `sys._is_gil_enabled()`: `False` на збірці 3.13.18+freethreaded; для звичайного CPython значення було `True`. Тепер потоки можуть одночасно виконувати Python-операції на кількох ядрах: 1 потік — 0.307 с, 8 потоків — 0.097 с, тобто 3.18× швидше **відносно одного потоку 3.13t**. За 9 потоків результат трохи погіршився до 0.106 с через накладні витрати, насичення ядер і можливі інші навантаження. Дисперсія окремих замірів означає, що ці числа слід читати як результати конкретного середовища, а не гарантію для кожної машини.

## Гонитви та інваріанти

GIL **не означає**, що складна операція на спільному `Counter` або списку атомарна: прочитати значення, обчислити нове і записати — кілька дій, між якими інший потік може змінити стан. Без GIL це особливо помітно. Якщо кілька воркерів роблять `shared_counter[word] += 1`, можна втратити частину оновлень. Виправлення — `threading.Lock` навколо критичної секції або, краще для мого випадку, **локальні словники воркерів** і детерміноване об'єднання після їх завершення. Я використав другий варіант: кожен воркер пише тільки у власний `Counter` та власний індекс, тому гонитви за спільні постінги немає навіть у free-threaded Python.

## Як відтворити

```bash
uv run python -m findex.cli generate --count 1000 --repetitions 20
uv run python bench_lab05.py data/ --repetitions 3
uv python install 3.13t
uv python find 3.13t
uv run python bench_lab05.py data/ --repetitions 3 --only-executor threads --python /шлях/до/python3.13t --output benchmark_lab05_313t.json
```

Результати зберігаються у JSON, графіки — PNG; README містить таблиці з медіанами трьох запусків. Середовище експерименту: Linux, 9 доступних логічних CPU, AMD EPYC 9V74 80-Core Processor. Вимірювання `resource` (CPU і RSS) орієнтовані на Linux; на Windows для аналогічного профілю потрібні інші системні API або `psutil`.
